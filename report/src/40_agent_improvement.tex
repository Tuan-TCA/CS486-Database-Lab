\section{AI Agent Improvement}

To improve the quality and consistency of AI-assisted database engineering, this project adopted a human-supervised agent improvement framework rather than a conventional one-shot prompting approach. Instead of repeatedly modifying generated outputs, the framework continuously improves the reusable knowledge of the AI agent through iterative evaluation and refinement.

The framework distinguishes between reusable knowledge and generated artifacts. Generated outputs are treated as intermediate benchmarks that reveal the current capability of the agent rather than final deliverables. Human evaluation identifies weaknesses, determines their root causes, and converts these findings into reusable knowledge. The updated knowledge is then incorporated into either the global Agent or a section-specific Skill before the next generation cycle.

This approach transforms prompt engineering into a systematic knowledge engineering process. Rather than correcting the same mistakes repeatedly, each iteration permanently improves the agent's capability, allowing later outputs to benefit from accumulated experience.

\subsection{Agent Improvement Framework}

\subsubsection{Objectives}

The proposed framework focuses on continuously improving the knowledge used by the AI agent throughout the project lifecycle. Instead of evaluating only the final deliverables, every intermediate benchmark is analyzed to identify reusable improvements.

The framework pursues the following objectives.

\begin{itemize}[leftmargin=2em]
	\item Improve the AI agent rather than manually correcting generated outputs.
	\item Build reusable knowledge that can be shared across multiple project sections.
	\item Increase consistency between business analysis, database design, SQL implementation, and query design.
	\item Reduce hallucinations through structured verification and human evaluation.
	\item Improve requirement traceability from the project specification to the final database artifacts.
	\item Establish a repeatable improvement workflow for future projects.
\end{itemize}

Unlike conventional prompt engineering, improvements are incorporated into reusable knowledge instead of individual outputs. Consequently, every subsequent generation benefits from previous evaluation results.

\subsubsection{Design Principles}

The framework is built upon four complementary design principles.

\paragraph{Separation of Concerns}

Reusable project knowledge is separated from section-specific methodologies. The global Agent stores knowledge shared by every deliverable, such as requirement traceability, naming consistency, and anti-hallucination rules. Each Skill contains methodologies, verification procedures, and checklists specific to one project section. This separation localizes improvements and prevents unrelated modifications from affecting other tasks.

\paragraph{Human-in-the-loop Evaluation}

The framework treats human reviewers as the final authority. Every generated benchmark is manually evaluated before knowledge is updated. Rather than automatically modifying files, the agent proposes improvements, while humans determine whether the proposed knowledge should be incorporated into subsequent iterations.

\paragraph{Iterative Knowledge Refinement}

The objective of each iteration is to improve reusable knowledge rather than a single document. Evaluation findings are transformed into permanent lessons that update either the global Agent or the appropriate Skill. As knowledge accumulates across iterations, later generations become progressively more complete, consistent, and reliable.

\paragraph{Requirement Traceability}

Every important design decision should be traceable to an explicit project requirement. During evaluation, reviewers verify that entities, relationships, constraints, business rules, and SQL implementations are supported by the original specification. This principle reduces unsupported assumptions and improves consistency throughout the database development process.

\subsection{Agent Architecture}

The proposed framework adopts a modular architecture that separates reusable project knowledge from section-specific methodologies. Rather than embedding all instructions within a single prompt, the framework organizes knowledge into independent components with clearly defined responsibilities. This design improves maintainability, supports iterative refinement, and enables reusable knowledge to evolve without introducing unintended side effects to other project sections.

Figure~\ref{fig:architecture} illustrates the overall architecture of the proposed framework.

\subsubsection{Global Agent}

The global Agent serves as the central repository of reusable project knowledge. Rather than describing how to generate a specific deliverable, it stores knowledge applicable throughout the entire database engineering process.

Typical responsibilities of the global Agent include

\begin{itemize}

	\item maintaining consistent terminology across all project deliverables;

	\item enforcing naming conventions for entities, attributes, relationships, and database objects;

	\item preventing unsupported assumptions through anti-hallucination rules;

	\item promoting explicit requirement traceability from project requirements to implementation;

	\item defining verification behaviors shared across all project sections.

\end{itemize}

The Agent is updated only when an identified lesson is considered globally reusable. Improvements specific to an individual project section remain within the corresponding Skill, preventing unnecessary coupling between unrelated tasks.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsubsection{Section Skills}

While the global Agent provides project-wide guidance, each section maintains an independent Skill responsible for specialized methodologies.

Rather than storing generated content, each Skill contains reusable knowledge such as generation procedures, verification checklists, consistency rules, anti-hallucination guidelines, and common mistakes discovered during previous iterations.

For example,

\begin{itemize}

	\item the Business Requirement Analysis Skill focuses on requirement extraction, actor identification, entity discovery, and business rule verification;

	\item the ER Design Skill specializes in conceptual modeling, relationship identification, and cardinality analysis;

	\item the Logical Design Skill performs relation mapping, key identification, normalization, and integrity verification;

	\item the SQL Implementation Skill focuses on schema generation, constraints, triggers, and implementation consistency.

\end{itemize}

Because each Skill evolves independently, improvements introduced into one section do not unintentionally affect other parts of the project.

\subsubsection{Discussion}

Compared with storing all project knowledge inside a single prompt, the proposed modular architecture provides several important advantages.

First, reusable knowledge is maintained centrally within the Agent and shared across all project sections. Second, section-specific improvements remain localized within individual Skills, preventing unintended interactions between unrelated tasks. Third, benchmark outputs and improvement documents provide an explicit record of knowledge evolution throughout the experiment. Finally, separating reusable knowledge from generated artifacts allows the framework to evolve continuously while preserving reproducibility and consistency across successive iterations.

\subsection{Iterative Improvement Process}

A key characteristic of the proposed framework is that improvements are applied to the agent rather than directly to the generated deliverables. Every evaluation cycle identifies weaknesses in the agent's understanding of the project requirements, transforms these observations into reusable knowledge, and incorporates the improvements into the next generation cycle. Consequently, the quality of generated artifacts gradually increases while reducing repetitive manual corrections.

\subsubsection{Improvement Strategy}

Each improvement cycle consists of four sequential activities.

\begin{enumerate}

	\item Generate an initial deliverable using the current version of the agent.

	\item Evaluate the generated result according to predefined quality criteria.

	\item Identify missing requirements, inconsistencies, or unsupported assumptions.

	\item Refine the corresponding knowledge component before generating the next version.

\end{enumerate}

This strategy ensures that every improvement addresses the underlying cause rather than only correcting the visible symptoms in a single document.

\subsubsection{Representative Improvements}

Several improvements substantially increased the quality of generated database artifacts.

\paragraph{Requirement Extraction}

Early generations occasionally omitted implicit business constraints described in the project specification. To address this issue, the requirement analysis skill was modified to explicitly identify business purposes, actors, entities, relationships, operational constraints, and exceptional situations before constructing any database model.

This improvement significantly increased requirement coverage during subsequent iterations.

\paragraph{Business Rule Coverage}

Database systems are driven not only by entities but also by operational constraints. Therefore, the improvement process emphasized extracting business rules before designing the schema.

Examples include

\begin{itemize}

	\item preventing overlapping approved bookings;

	\item prohibiting reservations for unavailable spaces;

	\item preserving historical booking records;

	\item enforcing approval authority based on staff roles.

\end{itemize}

By explicitly identifying these constraints, later iterations produced database schemas that more accurately reflected real operational requirements.

\paragraph{Naming Consistency}

Several early iterations used inconsistent terminology for identical concepts. Examples included different names for booking requests, maintenance records, and approval information.

A unified naming convention was therefore incorporated into the global agent, ensuring that

\begin{itemize}

	\item entity names remained identical across all documents;

	\item primary and foreign keys followed consistent conventions;

	\item SQL table names matched conceptual entities;

	\item attribute names remained unchanged throughout every project phase.

\end{itemize}

This significantly reduced inconsistencies between the ER diagram, relational schema, SQL implementation, and validation report.

\paragraph{Requirement Traceability}

One of the most important improvements introduced during later iterations was explicit requirement traceability.

Instead of merely producing database objects, the agent was instructed to justify every important design decision by referencing the corresponding business requirement.

This additional verification step reduced unsupported assumptions and improved the explainability of the overall database design.

\subsubsection{Discussion}

The iterative improvement process demonstrates that human evaluation remains an essential component of AI-assisted software engineering. While the language model efficiently generates initial solutions, expert review is required to identify subtle inconsistencies, missing requirements, and unsupported assumptions.

More importantly, incorporating evaluation feedback into reusable knowledge allows improvements to persist across future generations. This capability distinguishes the proposed framework from conventional prompt engineering, where corrections are repeatedly applied to individual outputs instead of improving the underlying generation process.

\subsection{Evaluation Methodology}

To ensure that each improvement cycle objectively enhanced the quality of the generated deliverables, every intermediate output was evaluated using a predefined assessment framework. Rather than relying on subjective impressions, the evaluation process employed consistent criteria throughout all iterations. The resulting observations were subsequently transformed into reusable knowledge that guided the next generation cycle.

\subsubsection{Evaluation Procedure}

Each iteration follows the same evaluation procedure.

\begin{enumerate}

	\item Generate one project deliverable.

	\item Compare the generated result against the project specification.

	\item Identify missing requirements, logical inconsistencies, and unsupported assumptions.

	\item Record improvement suggestions.

	\item Update the corresponding knowledge component.

	\item Regenerate the deliverable.

\end{enumerate}

Because every iteration uses identical evaluation criteria, improvements remain comparable throughout the entire project.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsubsection{Lessons Learned}

Several important observations were obtained throughout the improvement process.

\paragraph{Importance of Human Evaluation}

Although large language models efficiently generate initial database designs, manual review remains indispensable for identifying subtle logical inconsistencies that cannot easily be detected automatically.

\paragraph{Knowledge Reuse}

Updating reusable knowledge proved considerably more effective than repeatedly correcting individual outputs. Once incorporated into the agent, improvements automatically benefited every subsequent deliverable.

\paragraph{Requirement Traceability}

Explicitly linking database components to business requirements substantially reduced unsupported design decisions and improved overall explainability.

\paragraph{Modular Design}

Separating global knowledge from section-specific skills simplified maintenance and prevented unrelated modifications from propagating across the project.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsubsection{Threats to Validity}

Despite the encouraging results, several limitations should be acknowledged.

First, the evaluation relied primarily on expert human judgment rather than fully automated metrics. Different evaluators may therefore assign slightly different scores.

Second, the project focused on a single database engineering case study. Additional experiments involving different application domains would be necessary to evaluate the generalizability of the proposed framework.

Finally, improvements were assessed qualitatively through successive refinement cycles rather than through controlled experimental comparison with alternative prompting strategies.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsubsection{Discussion}

Overall, the proposed evaluation methodology demonstrates that systematic human-supervised refinement can substantially improve the reliability of AI-assisted database engineering. Rather than viewing prompt engineering as a one-time activity, the framework treats prompt and knowledge refinement as an iterative engineering process. The accumulated knowledge progressively improves requirement understanding, reduces inconsistencies, and increases the quality of generated database artifacts throughout the entire project lifecycle.
