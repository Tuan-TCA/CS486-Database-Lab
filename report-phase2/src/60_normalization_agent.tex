\section{Functional Dependencies and Normalization}

This section analyzes the functional dependencies (FDs) of the
relational schema and verifies whether the database satisfies the
Third Normal Form (3NF). The analysis is based on the primary keys,
foreign keys, and attribute dependencies represented in the ERD.

\subsection{Functional Dependencies}

A functional dependency $X \rightarrow Y$ means that the values of
attributes $X$ uniquely determine the values of attributes $Y$.

For this database, the functional dependencies are derived from the
candidate keys and the semantic meaning of each entity. Foreign keys
alone do not introduce additional functional dependencies in a
relation when the attributes determined by the referenced relation are
not stored in the child relation.

\subsection{Important Observation about Foreign Keys}

Foreign keys do not automatically create functional dependencies from
the foreign key to the attributes of the referenced relation.

For example, the following dependency exists in the
\texttt{SPACE\_TYPE} relation:

\[
\texttt{space\_type\_id}
\rightarrow
\texttt{space\_type\_name}.
\]

However, \nolinkurl{space_type_id} in \texttt{SPACE} does not determine
\nolinkurl{space_type_name} because \nolinkurl{space_type_name} is not an
attribute of \texttt{SPACE}. It is stored in the
\texttt{SPACE\_TYPE} relation.

Similarly,

\[
\texttt{role\_id} \rightarrow \texttt{role\_name}
\]

holds in \texttt{ROLE}, but it does not create a transitive dependency
inside \texttt{USERS}, because \texttt{role\_name} is not stored in
\texttt{USERS}.

This separation prevents unnecessary redundancy between related
entities.

\subsection{First Normal Form (1NF)}

A relation is in First Normal Form if:

\begin{enumerate}
    \item every attribute contains atomic values;
    \item there are no repeating groups; and
    \item each tuple can be uniquely identified by a key.
\end{enumerate}

All relations in the proposed schema satisfy these requirements.
Each attribute represents a single value, and each relation has a
defined primary key.

For example, \texttt{BOOKING\_REQUEST} stores one value for
\texttt{start\_time}, one value for \texttt{end\_time}, one value for
\texttt{purpose}, and so on. No attribute contains a repeating group
of values.

Therefore,

\[
\boxed{\text{All relations are in 1NF.}}
\]

\subsection{Second Normal Form (2NF)}

A relation is in Second Normal Form if:

\begin{enumerate}
    \item it is already in 1NF; and
    \item every non-prime attribute is fully functionally dependent on
    the whole candidate key.
\end{enumerate}

Most relations in the proposed schema have a single-attribute
candidate key, such as:

\[
\begin{aligned}
&\texttt{space\_code},\quad \texttt{user\_id},\quad
\texttt{booking\_id},\quad \texttt{decision\_id},\\
&\texttt{maintenance\_id},\quad \texttt{session\_id}.
\end{aligned}
\]

For a single-attribute key, a partial dependency cannot occur because
there is no proper subset of the key.

The two relations with composite keys are
\nolinkurl{BOOKING_NOTIFICATION} and \nolinkurl{AUTO_USAGE_POLICY}.

For \texttt{BOOKING\_NOTIFICATION}:

\[
(\texttt{booking\_id},\texttt{maintenance\_id},
\texttt{notification\_type})
\rightarrow
\texttt{notification\_time}.
\]

The only non-key attribute, \texttt{notification\_time}, depends on the
complete composite key. There is no FD from a proper subset of the key
to \texttt{notification\_time} specified by the ERD.

For \texttt{AUTO\_USAGE\_POLICY}, the relation contains only its
composite primary key and no non-key attributes. Therefore, partial
dependency is impossible.

Consequently,

\[
\boxed{\text{All relations are in 2NF.}}
\]

\subsection{Third Normal Form (3NF)}

A relation is in Third Normal Form if, for every non-trivial functional
dependency

\[
X \rightarrow A,
\]

at least one of the following conditions holds:

\begin{enumerate}
    \item $X$ is a superkey; or
    \item $A$ is a prime attribute.
\end{enumerate}

The schema satisfies the stronger condition that every determinant of
a non-trivial FD is a candidate key.

\subsubsection{Verification of Individual Relations}

\paragraph{\texttt{SPACE\_TYPE}}

The only non-trivial FD is:

\[
\texttt{space\_type\_id}
\rightarrow
\texttt{space\_type\_name}.
\]

Since \texttt{space\_type\_id} is the primary key, it is a superkey.

Therefore, \texttt{SPACE\_TYPE} is in 3NF.

\paragraph{\texttt{ROLE}}

\[
\texttt{role\_id}
\rightarrow
\texttt{role\_name}.
\]

Since \texttt{role\_id} is the primary key, the determinant is a
superkey. Therefore, \texttt{ROLE} is in 3NF.

\paragraph{\texttt{SPACE}}

\[
\begin{aligned}
\texttt{space\_code} \rightarrow \{&
\texttt{space\_type\_id},\ \texttt{space\_name},\ \texttt{building},\\
&\texttt{floor},\ \texttt{room\_number},\ \texttt{capacity},\\
&\texttt{current\_status}\}.
\end{aligned}
\]

The determinant \texttt{space\_code} is the primary key. Therefore,
all non-trivial dependencies satisfy the 3NF condition.

\paragraph{\texttt{USERS}}

\[
\begin{aligned}
\texttt{user\_id} \rightarrow \{&
\texttt{role\_id},\ \texttt{full\_name},\ \texttt{email},\\
&\texttt{phone\_number},\ \texttt{department},\\
&\texttt{account\_status}\}.
\end{aligned}
\]

The determinant is the primary key \texttt{user\_id}. Therefore,
\texttt{USERS} is in 3NF.

\paragraph{\texttt{FACILITY}}

\[
\begin{aligned}
\texttt{facility\_id} \rightarrow \{&
\texttt{space\_code},\ \texttt{facility\_name},\\
&\texttt{description}\}.
\end{aligned}
\]

Since \texttt{facility\_id} is the primary key, the relation satisfies
3NF.

\paragraph{\texttt{BOOKING\_REQUEST}}

\[
\begin{aligned}
\texttt{booking\_id} \rightarrow \{&
\texttt{user\_id},\ \texttt{space\_code},\ \texttt{start\_time},\\
&\texttt{end\_time},\ \texttt{purpose},\ \texttt{expected\_participants},\\

The determinant is the primary key \texttt{booking\_id}. Therefore,

\paragraph{\texttt{BOOKING\_NOTIFICATION}}

The candidate key is:

\[
K =
(\texttt{booking\_id},
\texttt{maintenance\_id},
\texttt{notification\_type}).

The non-trivial FD is:

\[
K \rightarrow \texttt{notification\_time}.

The candidate key is:

\[

(\texttt{space\_type\_id},\texttt{role\_id}).

non-trivial FD whose right-hand side is a non-prime attribute.
Consequently, the relation trivially satisfies 3NF.

\subsection{Proof of 3NF}

For every relation in the proposed database, the non-trivial
functional dependencies identified from the ERD have a determinant
that is a candidate key and therefore a superkey.

Formally, for every non-trivial FD

\[
X \rightarrow A,
\]

in the schema,

\[
X \text{ is a superkey}.
\]

Therefore, the 3NF condition is satisfied for every relation:

\[
\boxed{
\forall X \rightarrow A,\quad
X \text{ is a superkey}
}
\]

Thus,

\[
\boxed{
\text{The complete relational schema satisfies 3NF.}
}
\]

In fact, under the functional dependencies identified above, the
schema satisfies the stronger Boyce--Codd Normal Form (BCNF), because
every determinant of a non-trivial functional dependency is a
candidate key.

\[
\boxed{
\text{3NF is satisfied, and the relations are also in BCNF.}
}
\]

\subsection{Need for Further Decomposition}

No further decomposition is required to achieve 3NF because the
current relational schema already satisfies 3NF.

The decomposition of descriptive information into separate relations
such as \texttt{ROLE}, \texttt{SPACE\_TYPE}, and \texttt{SPACE} also
prevents redundant storage of attributes that belong to different
entities. For example, the role name is stored only in
\texttt{ROLE}, while \texttt{USERS} stores only the corresponding
foreign key \texttt{role\_id}.

Therefore, the final schema preserves the entity structure represented
by the ERD while avoiding partial and transitive dependencies within
the individual relations.
