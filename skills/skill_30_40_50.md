## 5. LaTeX Formatting Rules

### 5.1 Package Awareness

The following packages are already loaded in `main.tex` — use them freely:

- `tabularx` — for flexible-width tables
- `array` — for column formatting
- `float` — for `[H]` placement
- `listings` / `lstlisting` — for code blocks
- `tcolorbox` — for highlighted boxes (use `gitbox` environment if needed)
- `enumitem` — for customized lists
- `hyperref` — for links
- `caption` — table captions (note: `\captionsetup[table]{labelformat=empty}`)

### 5.2 Table Convention

Use `tabularx` with `\textwidth` for all tables:

```latex
\begin{table}[H]
\centering
\caption{Table Title}
\begin{tabularx}{\textwidth}{|l|X|}
\hline
\textbf{Column 1} & \textbf{Column 2} \\
\hline
Data & Data \\
\hline
\end{tabularx}
\end{table}
```

### 5.3 Code Blocks

Use `lstlisting` for SQL and directory structures:

```latex
\begin{lstlisting}[language=SQL, caption=Query Description]
SELECT column1, column2
FROM table_name
WHERE condition;
\end{lstlisting}
```

### 5.4 Naming Conventions

- Entity/Table names: use `\texttt{UPPER\_SNAKE\_CASE}` (e.g., `\texttt{BOOKING\_REQUEST}`)
- Attribute/Column names: use `\texttt{lower\_snake\_case}` (e.g., `\texttt{user\_id}`)
- Escape underscores in text mode: `\_`
- In `lstlisting` environments, underscores do NOT need escaping

### 5.5 Cross-References

- Do not use `\label` / `\ref` unless coordinated with other sections
- Use descriptive table captions
- Number subsections follow the document's `\setcounter{secnumdepth}{4}` setting

### 5.6 Consistency with Section 2

- Use the same formatting patterns as `report/src/20_db_design.tex`
- Same table style, same code block style, same list style
- Maintain identical naming for entities, attributes, and relationships throughout

- Evaluation scores MUST match `evaluation/overall-team-output.md` exactly
- Do NOT invent scores, improvement rounds, or lessons not documented in the source files

### 6.2 Content Synthesis

- Do NOT copy-paste raw content from the source files
- Rephrase and restructure content for a formal academic report tone
- Consolidate information — avoid repeating facts already covered in Section 2
- Use tables for structured data, prose for explanations and design rationale
- Keep each section within its page budget

### 6.3 Anti-Hallucination

- Do NOT add entities, attributes, or business rules not present in the source files
- Do NOT invent evaluation scores or improvement rounds
- Do NOT add tools, frameworks, or technologies not used in the project
- If something is ambiguous, flag it with a LaTeX comment `% TODO: verify`
- Do NOT mention specific LLM model names unless they are documented in the source files
- The agent framework uses: Agent.md, skill\_xx.md, evaluation\_xx.md, improveXX.md, and prompt files — do NOT invent additional components

### 6.4 Section 4 Specific Guidance

- Describe the **process** (how the agent was improved), not just the **results**
- Show the **evolution** of knowledge through iteration rounds
- Emphasize the **human-in-the-loop** aspect — humans evaluated and approved all changes
- Distinguish between **Agent updates** (global, cross-section) and **Skill updates** (section-specific)
- Present the improvement framework as a **reusable methodology**, not just a one-time exercise
- The LLM models used by the group should be mentioned as required by the project description, but only if documented; otherwise use a generic reference

## 9. Common Mistakes to Avoid

1. Writing `\documentclass` or `\begin{document}` in a sub-file
2. Using `tabular` instead of `tabularx` (causes overflow)
3. Forgetting to escape underscores in entity/attribute names outside code blocks
4. Inventing evaluation scores not present in the improve files
5. Inventing improvement rounds that did not occur
6. Adding tools or frameworks not used in the project (e.g., LangChain, AutoGPT)
7. Describing the agent as "autonomous" — it is human-supervised
8. Omitting the human-in-the-loop aspect of the improvement process
9. Using inconsistent naming between Section 3 and Section 2 (e.g., USER vs USERS)
10. Writing overly long prose that exceeds the page budget
11. Copying SQL code verbatim without explanation — always provide context
12. Presenting improvement history without showing the evolution (just listing final scores)
13. Omitting the distinction between Agent updates and Skill updates
14. Using 1:N cardinality for Booking\_Approval or Usage\_Session (must be 1:0..1)
15. Placing query results without explaining the business question they answer
16. Forgetting to mention triggers as part of the constraint implementation
17. Not referencing the actual output files when describing SQL implementation
